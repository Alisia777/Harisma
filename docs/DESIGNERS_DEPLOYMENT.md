# Развёртывание раздела «Дизайнеры»

## 1. Применить серверную миграцию

В Supabase SQL Editor от имени владельца проекта выполнить целиком
`docs/supabase_design_workspace_setup.sql`.

Миграция идемпотентна и включает:

- закрытые таблицы рабочей базы, версий и аудита с RLS;
- оптимистичную блокировку ревизий и восстановление версий;
- отсутствие новой ревизии при неизменном payload;
- хранение последних 100 версий и 2 000 событий аудита на бренд;
- автоматическую выдачу доступа из защищённого `app_metadata.portal_role`.

Роли `owner` и `designer` получают `editor`; `director` и `product` — `viewer`.
Триггер синхронизирует членство при создании аккаунта и изменении роли. Ручные
членства с `managed_by_role = false` триггер не удаляет.

### Файлы и фото задач

Workflow `Designers file storage` автоматически обновляет общий bucket
`portal-task-files`: включает фото, PDF, Office, ZIP, AI и PSD до 20 МБ.
Если workflow недоступен, выполнить в SQL Editor актуальную версию
`docs/supabase_task_attachments_setup.sql`. Первое фото задачи становится
обложкой карточки, а остальные файлы остаются доступными внутри задачи.

## 2. Проверить членство

```sql
select m.brand, u.email, m.access_level, m.managed_by_role, m.updated_at
from public.portal_design_workspace_members m
join auth.users u on u.id = m.user_id
order by m.brand, u.email;
```

## 3. Приёмка после публикации

1. Редактор открывает «Дизайнеры», создаёт тестовый проект и видит новую ревизию.
2. Повторное нажатие «Синхронизировать» без изменений не создаёт ревизию.
3. Наблюдатель видит проекты, историю и серверный аудит, но не видит действий записи.
4. Два редактора меняют одну карточку: второй получает выбор версии без перезаписи.
5. У пользователя без членства данные раздела не появляются даже из локального кеша.

## 4. Откат

Код портала можно откатить обычным revert PR. Серверные таблицы при откате кода
не удалять: они содержат историю и позволяют вернуть раздел без потери данных.
