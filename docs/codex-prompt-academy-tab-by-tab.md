## Главный принцип

Обучение должно быть не абстрактным, а рабочим:

```text
Открыл вкладку → понял, что здесь смотреть → понял, что можно менять → понял, когда данные обновляются → понял, что делать при ошибке → прошёл мини-тест.
```

На каждой вкладке должна появиться компактная кнопка:

```text
? Как пользоваться разделом
```

При клике открывается drawer справа с обучением именно по этой вкладке.

## Контент модулей по каждой вкладке

### 1. `dashboard` — Дашборд

**Цель:** сотрудник понимает общую картину и не делает выводы по неполным данным.

Обучить:

- где общий KPI;
- где графики;
- где сеть / площадка;
- где дата обновления;
- что означает статус синхронизации;
- как перейти от проблемы к профильной вкладке.

Ключевое правило:

```text
До 11:00 по Москве данные могут быть неполными. Сначала проверяем время обновления, потом делаем вывод.
```

Мини-тест:

1. Что проверяем первым при странных цифрах?
2. Можно ли делать финальный вывод до 11:00 МСК?
3. Куда идти, если просел заказ: воронка, цены, OOS, карточка, реклама?

---

### 2. `data-health` — Календарь

**Цель:** сотрудник понимает календарь акций, событий, SKU и контроль обновлений.

Обучить:

- где смотреть акции;
- где события;
- где SKU в календаре;
- как понять, что событие влияет на продажи;
- как проверять будущие периоды;
- как не путать календарь с задачником.

Сценарий:

```text
Открыть Календарь → выбрать период → проверить акции / события / SKU → понять влияние на продажи → при необходимости создать задачу в Tracker.
```

Мини-тест:

- куда смотреть перед анализом падения/роста в период акции;
- можно ли менять календарь без owner;
- что делать, если акция есть, а задачи на подготовку нет.

---

### 3. `control` — Задачи / Tracker

**Цель:** сотрудник умеет создавать и вести задачу как рабочий тикет, а не как vague-запись.

Обучить:

- задача отдела vs изменение из реестра;
- owner;
- дедлайн;
- критерий готовности;
- комментарий при смене статуса;
- блокер;
- next step;
- когда эскалировать смежников;
- как переводить: Идея → Валидация/Верификация → Работа → Проверка → Завершено.

Сценарий:

```text
Открыть Задачи → создать тикет → написать результат → назначить owner → поставить срок → добавить чек-лист → вести статус → закрыть только после критерия готовности.
```

Мини-тест:

- что обязательно должно быть у тикета;
- можно ли писать «улучшить маркетинг»;
- что делать, если смежный отдел не даёт срок;
- почему статус без комментария плохой.

---

### 4. `documents` — Хранилище

**Цель:** сотрудник знает, где искать регламенты, инструкции, файлы и актуальные версии.

Обучить:

- где файлы;
- где ссылки;
- где описание документа;
- как понять актуальность версии;
- что делать, если регламент изменился;
- где искать обучение / базу знаний.

Сценарий:

```text
Открыть Хранилище → найти документ → проверить дату/версию → использовать актуальную инструкцию → если нет документа, создать задачу на добавление регламента.
```

Мини-тест:

- можно ли работать по старой версии файла;
- что делать, если инструкции нет;
- где хранить запись встречи / артефакты процесса.

---

### 5. `executive` — Руководителю

**Цель:** руководитель видит риски, решения, итог и понимает, что требует эскалации.

Обучить:

- где риски;
- где управленческие решения;
- где итог по направлениям;
- как читать отклонения;
- как перейти в первичный источник;
- когда создавать эскалацию.

Сценарий:

```text
Открыть Руководителю → посмотреть риск → открыть первичный раздел → проверить владельца и срок → принять решение / назначить follow-up.
```

Мини-тест:

- что делать с красным риском без owner;
- можно ли принять решение без первичного источника;
- когда нужна встреча со смежниками.

---

### 6. `sku-plan-fact` — План-факт SKU

**Цель:** сотрудник понимает план, факт, чек, ДРР и отклонения по SKU.

Обучить:

- где план;
- где факт;
- где чек;
- где ДРР;
- как читать отклонение;
- как отличать проблему спроса от проблемы наличия/цены/рекламы.

Сценарий:

```text
Открыть План-факт SKU → выбрать SKU/MP/период → сравнить план и факт → проверить чек/ДРР → перейти в цены, воронку или OOS.
```

Мини-тест:

- что проверяем при факте ниже плана;
- куда идти, если ДРР высокий;
- почему нельзя смотреть только выручку без маржи/чека.

---

### 7. `repricer` — Репрайсер

**Цель:** сотрудник умеет читать рекомендации и не применяет опасные цены.

Обучить:

- текущая цена;
- рекомендованная цена;
- minimum price / price floor;
- риск `ok/warn/danger`;
- файл выгрузки/загрузки;
- проверка перед загрузкой;
- что делать после загрузки;
- когда эскалировать.

Сценарий:

```text
Открыть Репрайсер → выбрать MP/SKU → проверить текущую цену → сравнить с min price → посмотреть риск → подготовить файл → проверить перед загрузкой → после обновления сверить цену на площадке.
```

Мини-тест:

- что делать, если цена ниже минимума;
- можно ли загружать цену без проверки маржи;
- где смотреть риск;
- что проверить после загрузки.

---

### 8. `prices` — Цены

**Цель:** сотрудник умеет проверять цену, маржу, оборот и СПП.

Обучить:

- где актуальная цена;
- где маржа;
- где оборот;
- где СПП/скидка;
- как сверить цену с WB/Ozon/Я.Маркет;
- как понять расхождение после обновления;
- когда создавать задачу.

Сценарий:

```text
Открыть Цены → найти SKU → проверить текущую цену → проверить скидку/СПП → проверить маржу → сверить с MP → если расхождение подтверждено, создать задачу.
```

Мини-тест:

- что проверяем перед жалобой «цена не такая»;
- почему цена в портале и на MP может отличаться;
- что делать, если цена ушла ниже коридора.

---

### 9. `order` — Заказ товара

**Цель:** сотрудник понимает потребность, кластеры, склады и поставки.

Обучить:

- где кластеры;
- где склады;
- где поставки;
- как читать потребность;
- как связать заказ товара с OOS;
- что делать, если поставка не закрывает потребность.

Сценарий:

```text
Открыть Заказ товара → выбрать кластер/склад/SKU → проверить остаток и потребность → сверить поставку → создать задачу на действие.
```

Мини-тест:

- куда смотреть при риске OOS;
- что делать, если склад пустой, а продажа идёт;
- почему нельзя смотреть только общий остаток без кластера.

### 10. `oos-control` — OOS контроль

**Цель:** сотрудник умеет видеть пустые полки, потери и необходимые меры.

Обучить:

- что такое OOS;
- где пустые полки;

- где меры;

- куда передавать проблему: заказ товара, логистика, карточка, реклама.

Сценарий:

```text
Открыть OOS → найти SKU с потерями → проверить кластер → проверить поставку → назначить меру → создать/обновить задачу.
```

Мини-тест:

- что важнее: количество SKU в OOS или потерянная выручка;
- куда идти после выявления OOS;
- можно ли запускать рекламу на SKU без остатка.

### 11. `sku-contour` — SKU workspace

Мини-тест:

- что делать с SKU без owner;

### 17. `content-factory` — Контент-завод / логический модуль

**Цель:** сотрудник понимает, где ТЗ, статусы контента, проверка и связь с запуском новинки.

Если отдельной вкладки нет, показать как модуль в Академии и drawer для `documents`, `control`, `launches`.

Обучить:

- где ТЗ;
- где материалы;
- где owner;
- где дедлайн;
- где статус;
- где проверка результата;
- что делать, если креатор сделал не по ТЗ;
- как не грузить контент постфактум без контроля;
- как связать контент с карточкой, новинкой и рекламой.

Сценарий:

```text
Открыть модуль Контент-завод → найти ТЗ → проверить статус → открыть материалы → проверить результат → при отклонении создать задачу с комментариями → связать с запуском новинки.
```

Мини-тест:

- можно ли принимать контент без ТЗ;
- что делать, если нет дедлайна;
- где фиксировать отклонение;
- почему контент должен быть готов до запуска карточки/рекламы.

## JS acceptance criteria по вкладкам

1. Для каждого активного `.nav-btn[data-view]` из `index.html` есть объект в `ACADEMY_TAB_MODULES` или явный fallback.
2. На каждой активной вкладке появляется `academy-help-btn`.
3. Если секция вкладки ещё пустая/перерендеривается позже, кнопка добавляется через `MutationObserver` без дублей.
4. Drawer открывается для правильного `viewId`.
5. Кнопка `Открыть вкладку` переводит на нужный `viewId`.
6. В модуле `launches` есть сценарий заведения новинки.
7. В модуле `repricer` есть сценарий работы с min price и risk.
8. В модуле `prices` есть сценарий сверки цены.
9. В модуле `product-leaderboard` есть сценарий воронки.
10. В модуле `content-factory` есть сценарий ТЗ/статусов/проверки контента, даже если отдельной вкладки пока нет.
11. В каждом модуле есть quiz минимум из 3 вопросов.
12. Проходной балл — 80%.
13. Progress сохраняется в `localStorage`.
14. Первый вход показывает базовый маршрут и тест.
15. Все тексты безопасно экранируются.
16. Все классы начинаются с `academy-`.
17. Нет external dependencies.
18. Работает mobile.
19. Учитывается `prefers-reduced-motion`.
20. `npm run portal:tabs-smoke` проходит без ошибок.
